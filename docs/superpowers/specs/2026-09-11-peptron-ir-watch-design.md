# 펩트론 웹사이트 변경 감지 → 텔레그램 알림 (설계안)

- 작성일: 2026-09-11
- 대상 사이트:
  - IR 사이트: https://peptron.irupsite.co.kr/Default2.aspx
  - 본사 사이트: https://www.peptron.co.kr/ (뉴스/게시판 등)
- 상태: **검토 대기** (승인 후 구현 계획 작성)

---

## 1. 목적

펩트론이 웹에 공개한 콘텐츠가 **새로 올라오거나(신규)**, **조용히 수정되거나(수정)**,
**소리 없이 내려가는(삭제)** 경우를 텔레그램으로 즉시 알림받는다.

특히 중요한 것은 **"수정"과 "삭제"** 쪽이다. FAQ·IR자료·뉴스 게시글은 표기 날짜를 그대로 둔 채
본문 문구만 바뀌거나, 게시글·링크가 예고 없이 사라지는 일이 있는데, 사람 눈으로는 사실상 못 잡는다.
이 시스템은 **한 글자·링크 하나 단위의 변화까지 감지하고, 무엇이 어떻게 바뀌었는지 diff로 보여준다.**

### 이 도구가 하는 것 / 하지 않는 것

- **한다**: 이미 공개된 페이지가 바뀌거나 삭제되는 것을 감지한다. 공개되는 순간을 사람보다 빠르게 잡는다.
- **하지 않는다**: 공개 목록에 없는 글 번호를 찔러보거나, 숨김(비공개) 처리된 항목을 서버에서 꺼내오지 않는다.
  아직 공개되지 않은 상장사 자료를 미리 빼내는 것은 자본시장법상 미공개중요정보 문제로 직결되고,
  이 플랫폼은 여러 상장사가 공유하므로 다른 회사 미공개 자료 접근이기도 하다. (§13 참조)

> **참고**: 실제 운영 중인 유사 모니터의 알림 예시에서 확인된 감지 사례 —
> ① FAQ 문항의 오타 한 글자 수정("LUNA PHLEX™와는" → "LUNA PHLEX™는"),
> ② 본사 뉴스 게시글 링크 삭제. 둘 다 **공개 콘텐츠의 변화**이며 이 설계가 겨냥하는 대상이다.

## 2. 사이트 구조 조사 결과 (실측)

### 2.1 IR 사이트 — `Default2.aspx`

한 페이지 안에 모든 섹션이 들어 있다. 응답 UTF-8, 인증·세션 불필요, 단순 GET(약 300KB).

| 섹션 ID | 이름 | 데이터 위치 | 항목 식별자 |
|---|---|---|---|
| `section001` | 경영공시(실적자료) | 페이지 HTML `<table>` | 제목 + 날짜 |
| `section004` | 공시정보(DART) | 페이지 HTML `<table>` | `showRcept(접수번호)` → **접수번호** |
| `section007` | **FAQ** | 페이지 HTML `.faq-list li` (본문 포함) | 제목 + 날짜 |
| `section009` | **IR자료실** | 목록은 HTML, **본문은 별도 AJAX** | `popOpen(...)` 마지막 인자 → **IRActivityID** |
| `section011` | 주주 문의게시판 | 페이지 HTML | — (**감시 제외**, §12) |

**IR자료실 본문 API** (동작 확인, HTTP 200 / JSON):

```
GET /IRActivity/Detail2AJAX.aspx?IRActivityID=246
```

이 API는 화면에 안 보이는 필드까지 내려준다 — 그래서 **"어느 필드가 변하는지 미리 맞히지 않고,
서버가 주는 모든 필드를 통째로 지문(fingerprint)으로 저장해 하나라도 달라지면 알린다."**

```json
{
  "IRActivityID": 246,
  "Subject": "펩트론, CPHI Milan 2026 및 BioJapan 2026 참가",
  "Description": "<h3>...본문 HTML 전체...</h3>",
  "FileName": "",
  "RegisterDate": "/Date(1788910345000)/",   // 초 단위 — 화면엔 날짜만 표기됨
  "DeleteFlag": "N",                           // 글 숨김/복구 상태
  "MainFlag": "Y"                              // 메인 노출 여부
}
```

`RegisterDate`는 초 단위 타임스탬프라, 같은 날 안에서 글이 다시 저장되면 화면은 그대로인데 이 값이 움직인다.
`RegisterDate`가 수정 시 실제로 갱신되는지는 아직 확증하지 못했으나, **전 필드를 통째로 비교하므로
어느 필드가 정답이든 놓치지 않는다.** 첫 수정이 발생하는 순간 "실제로 변하는 필드"가 무엇인지도 알려준다.

### 2.2 본사 사이트 — `www.peptron.co.kr`

정적 HTML(UTF-8). 뉴스/게시판 목록 페이지가 링크 집합으로 구성된다 (동작 확인, HTTP 200):

- 목록: `https://www.peptron.co.kr/ds4_1_1.html` (뉴스 목록)
- 상세: `...ds4_1_1.html?c=view&db=newsp&no=101`

목록 페이지는 **게시글 링크 집합**을 추출해 비교한다. 링크가 추가되면 신규,
사라지면 **삭제(게시글 내림)** 로 판정한다. 참고 모니터가 실제로 이 링크 삭제를 잡아냈다.

## 3. 감시 범위 (설정 파일로 관리)

감시 대상은 `watch_config.yaml`에 URL 목록으로 정의한다. 각 항목은 **페이지 유형**을 가지며,
유형에 따라 추출·비교 방식이 달라진다. 나중에 URL 추가/삭제가 코드 수정 없이 가능하다.

| 키 | 대상 | 페이지 유형 | 비교 방식 | 잡히는 변화 |
|---|---|---|---|---|
| `ir_faq` | IR FAQ (section007) | `IR_FAQ` | 본문 텍스트 줄 diff | 신규·조용한 본문 수정·제목/날짜 변경 |
| `ir_activity` | IR자료실 (section009) | `IR_ACTIVITY` | 목록 + 항목별 전체 필드 비교 | 신규·본문 수정·첨부 교체·숨김/삭제 |
| `ir_disclosure` | 공시정보 (section004) | `IR_TABLE` | 접수번호 기준 목록 비교 | 신규 공시·기재정정 |
| `ir_earning` | 경영공시 (section001) | `IR_TABLE` | 제목+날짜 기준 목록 비교 | 신규 실적자료·변경 |
| `corp_news` | 본사 뉴스 목록 | `LINK_LIST` | 링크 집합 diff | 게시글 신규 등록·**삭제** |
| `corp_*` | 본사 기타 페이지 | `GENERIC_TEXT` | 정규화 텍스트 줄 diff | 임의 페이지 본문 변경·링크 삭제 |

**페이지 유형별 추출기**
- `IR_*`: §2.1의 섹션 구조를 안다.
- `LINK_LIST`: 페이지 내 유효 링크(`<a href>`) 집합만 추출 → 추가/삭제 판정.
- `GENERIC_TEXT`: 구조를 모르는 임의 페이지. 본문 텍스트를 정규화해 줄 단위 비교.

## 4. 알림 강화 필드 (참고 모니터 형식 반영)

각 변경 이벤트에는 아래 메타데이터를 붙여, 중요한 변화가 잡음에 묻히지 않게 한다.

| 필드 | 의미 | 산출 방식 |
|---|---|---|
| **구분** | 이벤트 종류 | `신규 게시글` / `기존 게시글 수정` / `게시글 삭제` / `내부 링크 삭제` |
| **페이지 분류** | 대상 성격 | `IR` / `BOARD_LIST` / `DISCLOSURE` / `NEWS` (config에 지정) |
| **중요도** | 우선순위 | 아래 규칙으로 `CRITICAL` / `HIGH` / `NORMAL` |
| **변경 비율** | 얼마나 바뀌었나 | (변경된 줄 수 ÷ 전체 줄 수) × 100, 소수 1자리 |
| **관련 키워드** | 워치리스트 매칭 | 변경 내용에 워치리스트 단어가 있으면 나열 |
| **사건 ID** | 이벤트 고유번호 | `EVT-` + (대상키+diff) SHA256 앞 10자리 |
| **발견 시각** | 감지 시각 | KST |

**워치리스트(초기값, 설정으로 수정 가능)**: `일라이릴리`, `릴리`, `Lilly`, `기술이전`, `계약`, `공동연구`,
`SmartDepot`, `LUNA PHLEX`, `임상`, `승인`, `마일스톤`, `라이선스`

**중요도 규칙**
- `CRITICAL`: 워치리스트 키워드가 포함된 변경 / 공시(DISCLOSURE) 신규 / 게시글·링크 삭제
- `HIGH`: FAQ·IR자료 본문 수정, 신규 게시글
- `NORMAL`: 그 외 사소한 변경(공백·문장부호 등은 §6 정규화로 애초에 무시됨)

> 참고 모니터의 오타 수정 사례가 `CRITICAL`로 뜬 것은 변경 내용에 `SmartDepot` 키워드가 있었기 때문 —
> 위 규칙으로 동일하게 재현된다.

## 5. 실행 환경

**GitHub Actions cron, public 리포지토리.** 목록 폴링은 가벼우므로 **최대한 짧은 간격(5분)** 으로 돌린다.

- **왜 public**: 5분 간격이면 실행 횟수가 많아 private 무료 한도(2,000분)를 초과해 과금된다.
  public은 Actions 무료 무제한. 저장 내용은 이미 공개된 페이지 텍스트뿐이고,
  **텔레그램 토큰·chat_id는 코드가 아니라 GitHub Secrets에 보관**한다.
- **제약**: GitHub Actions cron은 정시 실행을 보장하지 않아, 혼잡 시 5분이 10~20분으로 밀릴 수 있다.
  초 단위 속도가 꼭 필요하면 나중에 PC 상시 실행을 병행한다(코드 그대로 재사용).

## 6. 구조

```
peptron-watch/
├── main.py                     # 전체 흐름 조율
├── watch_config.yaml           # 감시 대상 URL·유형·분류·워치리스트
├── peptron_watch/
│   ├── fetch.py                # HTTP (재시도·백오프)
│   ├── extract.py              # 페이지 유형별 → 구조화 스냅샷
│   ├── compare.py              # 이전 vs 현재 → 변경 이벤트
│   ├── enrich.py               # 중요도·변경비율·키워드·사건ID 부여
│   ├── render.py               # 이벤트 → 텔레그램 메시지
│   ├── notify.py               # 텔레그램 전송
│   └── state.py                # 스냅샷 읽기/쓰기
├── state/                      # 스냅샷 (Actions 자동 커밋 = 변경 이력)
├── tests/
│   ├── fixtures/               # 실제 응답 저장본
│   └── test_*.py
├── .github/workflows/watch.yml
├── requirements.txt
└── README.md                   # 봇 토큰 발급~배포 단계별 안내
```

`extract`는 네트워크를 모르고, `compare`는 HTML을 모르며, `render`는 텔레그램을 모른다.
저장된 픽스처만으로 추출·비교·강화·렌더링을 전부 테스트할 수 있다.

## 7. 텍스트 정규화 규칙 (오탐 방지 핵심)

비교 전 다음을 수행해, 관리자가 저장만 다시 눌러 생기는 변화는 무시하고
**사람이 읽는 글자가 실제로 바뀐 경우에만** 알린다.

1. `<script>`, `<style>` 제거
2. `<br>`, `</p>`, `</li>` → 줄바꿈, 나머지 태그 제거
3. HTML 엔티티 디코드
4. 줄 단위 좌우 공백 제거, 연속 공백 1칸, 빈 줄 최대 1개
5. `data-start`, `data-section-id` 등 편집기 자동 생성 속성은 태그와 함께 제거됨

## 8. 동작 흐름

```
1. state/*.json 로드
2. watch_config의 각 대상에 대해:
   - fetch → 유형별 extract → 이전 스냅샷과 compare
   - IR자료실은 각 IRActivityID마다 Detail2AJAX 호출해 전체 필드 병합
3. 변경 이벤트에 enrich(중요도·비율·키워드·사건ID) 부여
4. 이벤트를 중요도 순으로 렌더링 → 텔레그램 전송
5. 스냅샷 갱신 후 커밋 & 푸시 ([skip ci])
```

**변경 이벤트**: `NEW`(🆕) / `MODIFIED`(✏️) / `REMOVED`(🗑️).
`MODIFIED`는 제목/날짜/본문/첨부 중 무엇이 바뀌었는지 구분한다.

**첫 실행(baseline)**: state가 비어 있으면 **알림 없이 기준선만 저장**한다.
대신 "감시 시작 — 현재 FAQ N건, IR자료 N건, 공시 N건, 뉴스 N건을 기준선으로 저장" 시작 알림 1회.

## 10. 오류 처리

**조용히 죽는 것이 최악**이다 — 알림이 안 오면 "변화 없음"으로 오해하므로 감시 중단을 반드시 알린다.

| 상황 | 처리 |
|---|---|
| 네트워크/타임아웃 | 3회 재시도(2·4·8s). 실패 시 **스냅샷 미갱신** 후 종료 → 다음 회차 재시도 |
| 연속 6회(~30분) 실패 | ⚠️ "감시가 30분째 실패 중" 알림 1회 (복구 전까지 재발송 안 함) |
| 섹션/구조 못 찾음 | ⚠️ "사이트 구조 변경 의심 — 코드 점검 필요" 알림, 해당 대상만 갱신 보류 |
| IR 본문 AJAX만 실패 | 해당 항목 이전 본문 유지, 목록 변경만 판정 (본문 오탐 방지) |
| 텔레그램 전송 실패 | 3회 재시도. 최종 실패 시 **스냅샷 미갱신** → 다음 회차 재알림 (유실 방지) |

연속 실패 카운터는 `state/health.json`.

## 11. 테스트

`tests/fixtures/`에 실제 응답 저장, 네트워크 없이 검증.

- 추출: 저장 HTML/JSON에서 각 유형 항목이 정확히 나오는가
- 정규화: 공백/개행/엔티티만 다른 두 입력이 **같게** 판정되는가 (오탐 방지)
- 비교 신규/수정/삭제: 각 이벤트가 정확히 1건씩
- **변화 없음**: 같은 입력 두 번 → 이벤트 0개 (가장 중요)
- **본문 수정**: 제목·날짜 동일, 한 문장만 바꾼 픽스처 → `MODIFIED(본문)` + 정확한 diff
- **링크 삭제**: LINK_LIST에서 링크 1개 제거 → `REMOVED`
- 강화: 워치리스트 단어 포함 시 `CRITICAL`, 변경비율 계산, 사건ID 일관성
- 렌더링: 4,096자 초과 시 잘림
- 첫 실행: 빈 state에서 변경 알림 미발송
- 텔레그램은 mock (실제 발송 안 함)

## 13. 하지 않는 것 (명시)

공개 목록에 없는 `IRActivityID`(예: 247, 248…)를 순차로 찔러보거나 `DeleteFlag='Y'`(숨김) 항목을
꺼내오는 기능은 **만들지 않는다.** 이는 상장사가 공개하지 않은 자료를 공개 전에 취득하는 것으로
미공개중요정보 문제로 직결되며, 이 플랫폼은 여러 상장사 공유라 타사 미공개 자료 접근이기도 하다.
이 도구는 **이미 공개된 콘텐츠의 변화·삭제만** 감지하고, "공개되는 순간"을 빠르게 잡는 데 집중한다.
